PSB the summary of the patch (f2fs: allocate HOT_DATA for IPU writes), in the same format:
Issue in current segment-type selection:
Data written during fdatasync or a small fsync is marked with the FI_NEED_IPU flag.
__get_segment_type_6() treats that data like ordinary file data, so it is classified WARM unless the file is hot or COW.
For IPU writes, f2fs_inplace_write_data() still calls __get_segment_type() to set fio->temp, the write hint. So IPU writes go out with a WARM hint.
This data is rewritten often, so mixing it with warm data lowers segment invalidity and makes GC costlier.
Solution proposed by patch:
Adds one condition in __get_segment_type_6() (fs/f2fs/segment.c): if is_inode_flag_set(inode, FI_NEED_IPU), return CURSEG_HOT_DATA.
No new lock, struct, CONFIG option or on-disk change.
Cold files, GC-moved pages and aligned writes keep their type, because their checks run earlier.
It only takes effect with active_logs=6, the default.
Side effect: the check is on the fsync flag, not the real IPU decision. Out-of-place writes in the same fsync window, such as appends or any write in mode=lfs, also go to the HOT log.
Impact on UFS:
The IPU write LBA does not change. Only the hint on the bio changes, WARM to HOT, and the CPU cost is one bit test per page.
UFS sees a difference only if your vendor UFS or block code uses bi_write_hint.
The read path is not touched.
GC is where a gain is expected, since hot segments free up faster. The HOT section may rotate slightly faster under fsync-heavy loads.
The patch is not in 6.12.38 (it appears in v6.18.x), so it needs a backport.
