The bug is in the block layer's iteration helpers, not just in sd.c. blk_next_copy_bio() and blk_copy_bio_count() can't get past the request's own bio into the copy context list. Any driver that uses them gets a wrong answer, so the fix belongs in blk-copy.c.
blk-copy.c.iter.patch: the helper now continues into ctx->bios after the request's own bio.
This relies on blkdev_copy_chunk() submitting all source bios before all destination bios. The list therefore always ends with a destination bio, and a source bio with no successor can only be the detached head bio.
It needs no header change.

2. Verifying multi-source commands from the trace
What the trace shows: only the 16-byte CDB, not the parameter list payload, so you can't read the descriptors themselves. Instead you check four values in the CDB against dmesg.
c0 | 00 00 00 00 00 14 62 4b | 00 00 cf | 00 | 00 10 | 00
op | bytes 1-8: dst LBA     | 9-11: total blocks | | 13-14: param length |
Descriptor count. Divide the parameter length (bytes 13–14) by 16. It must equal SRC_SEGS in dmesg.
Total blocks. Bytes 9–11 must equal BLKS in dmesg.
Destination LBA. Bytes 1–8 equal FIRST_DST_PBA plus a fixed partition offset.
For sda11 the offset is 0xE4FA8. I checked it on four commands.
For sdg the offset is 0.
Pairing. Match each attempt to its command by timestamp. The ATTEMPT line is about 2 ms before the trace dispatch, so pair them by the destination LBA, not the time alone.
Healthy single-source example, sda11, 1385.45 s:
dmesg: FIRST_DST_PBA=0x611b9 BLKS=234 SRC_SEGS=1.
Trace: ... 14 61 61 | 00 00 ea | 00 | 00 10.
Destination LBA is 0x611b9 + 0xE4FA8 = 0x146161, which matches.
Blocks are 0xea = 234, which matches.
Parameter length is 0x10 = 16 bytes = 1 descriptor, which matches SRC_SEGS=1.
Broken multi-source example, sda11, 1508.33 s:
dmesg: FIRST_SRC_PBA=0x5e800 FIRST_DST_PBA=0x612a3 BLKS=416 SRC_SEGS=2.
Trace: c0 00 00 00 00 00 14 62 4b 00 00 cf 00 00 10 00.
The destination LBA 0x14624b matches (0x612a3 + 0xE4FA8).
The block count is 0xcf = 207, not 416.
The parameter length is 0x10, so 1 descriptor, not 2.
So only the first source run was copied, and 209 blocks were not.
Two more from the same trace:
1631.21 s: BLKS=314, SRC_SEGS=3. The trace has 111 blocks and 1 descriptor.
1999.85 s: BLKS=427, SRC_SEGS=12. The trace has 27 blocks and 1 descriptor.

First source LBA, for reference. The first descriptor's source LBA would be FIRST_SRC_PBA + 0xE4FA8. For 1508.33 s that is 0x5e800 + 0xE4FA8 = 0x1437a8. The trace can't confirm it, because the descriptor payload isn't traced. If you want to check descriptor contents, a debug print of the buffer in sd.c would show them.
On sdg the multi-segment attempts in your dmesg are a different failure. All five have SRC_SEGS=1 DST_SEGS=2, and none appears in the trace. They are rejected before dispatch, which is the safe outcome. For comparison, a healthy sdg command at 480.23 s has FIRST_DST_PBA=0x10c04 and BLKS=34. The trace shows 01 0c 04, 00 00 22 (34 blocks) and 00 10.
The pass rule for any run: for every command, block count equals BLKS and parameter length equals 16 times SRC_SEGS. Any mismatch means a short copy, and the integrity check should then also fail.
