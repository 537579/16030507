A short copy is a copy command that moves only part of the data the caller asked for, yet completes with GOOD status.
In sd_setup_oppo_copy_offload(), only the first source bio sits on the request (rq->bio). The remaining bios of the same copy sit on ctx->bios. The old code counted and walked sources with blk_copy_bio_count() and blk_next_copy_bio(), which follow bi_next from rq->bio and never reach the context list. So it sees one source, and it takes the block count from blk_rq_sectors(rq), which covers the first bio only.
The command that goes to the device therefore has:
one descriptor, for the first source run only;
a block count equal to the first run's length.
The device copies exactly that and reports success. The caller was told the whole range was copied, so nothing reports an error.
Which callers are affected
This is not specific to F2FS GC. It affects any caller of blkdev_copy_offload() that gives one destination range and more than one source range, where the queue limit max_copy_src_segments is above 1. It has to be that way round:
Several sources into one destination: the code sees 1 source and 1 destination, so the count check passes. Data is silently short-copied.
Several sources and several destinations: the code sees 1 source and N destinations, so the count check fails. The request is rejected with an I/O error, which is safe.
One source and several destinations: also rejected with an error, which is safe.
One source and one destination: correct. This is all callers that pass a single segment each.
I only know of F2FS GC. I haven't seen the other callers, so ask the developers to grep for blkdev_copy_offload and check whether any passes more than one source segment.
Evidence to include
Trace against dmesg: F2FS GC attempts with SRC_SEGS of 2, 3 and 12 had BLKS of 416, 314 and 427. The SCSI trace for the same commands shows CDB block counts of 207, 111 and 27, each with a 16-byte parameter list. Every attempt with SRC_SEGS=1 matched exactly.
Benchmark: gcbench with offload on and alternating source blocks failed integrity in all 15 runs, with identical bad counts per setting. The single-run contig pattern had 0 bad. dmesg showed no I/O errors, and F2FS committed the result.
What the patch does
Walks all copy bios, the request's own bio first and then ctx->bios.
Validates before it allocates anything: exactly one destination bio, 1–256 sources, source blocks equal to destination blocks, at most 131072 blocks, and sizes aligned to the logical block size. Anything else fails with BLK_STS_IOERR.
Takes the total block count from the sum of all sources.
Sizes the parameter buffer to the 16 × N descriptor bytes instead of the copy size.
Removes the dead param_len < 0 check.
Caveats to state
I have not compiled it. It uses struct bio_copy_offload_ctx fields directly, so the definition must be visible in sd.c.
The parameter buffer length changes, from up to 1 MiB on a 4 KiB page to the descriptor bytes. That should be right, but it is new behaviour on the hardware.
The firmware's handling of more than one descriptor is unconfirmed. The trace so far shows only single-descriptor commands.
The cleaner long-term fix is in blk-copy.c, so the iteration helpers cross from the request's bio to the context list. Setting max_copy_dst_segments to 1 where the queue limits are set would also prevent the multi-destination rejections.
